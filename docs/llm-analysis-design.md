# LLM 분석 설계

## 1. 목적

정제된 뉴스·댓글을 LLM Batch API로 분석해 감정, 토픽 후보, 키워드와 요약을 생성하는 목표 설계입니다.

현재 LLM 제출·결과 적재 코드는 아직 구현되지 않았습니다. 토큰·비용 관측은 직접 원장만 구축하는 방식 대신 Langfuse 도입을 검토하도록 계획을 변경했습니다.

## 2. 처리 흐름

```text
PostgreSQL의 분석 대기 문서 조회
→ Batch 요청 JSONL 생성
→ LLM Batch API 제출
→ Batch ID와 요청 custom ID 기록
→ 완료·오류·만료 상태 확인
→ 결과 JSON Schema 검증
→ 감정·토픽·요약 저장
→ 실패·누락 요청 재처리
→ Langfuse로 토큰·비용·지연 관측
```

수집과 정제는 LLM API 상태와 무관하게 계속 수행합니다. 분석 실패 문서는 `pending` 또는 `retry` 상태로 유지해 다음 실행에서 처리합니다.

## 3. 문서별 분석 결과

한 문서에 대한 요청에서 가능한 한 다음 결과를 함께 생성해 중복 입력 토큰을 줄입니다.

- 긍정·중립·부정 분류
- 분류 신뢰도 또는 근거 점수
- 토픽 후보
- 대표 키워드
- 짧은 요약

응답은 자유 형식 텍스트가 아니라 검증 가능한 JSON Schema로 제한할 예정입니다.

## 4. 토픽 통합과 집계

문서별 토픽 표현을 그대로 집계하면 같은 의미가 여러 이름으로 나뉠 수 있습니다.

| 단계 | 역할 | 결과 |
|---|---|---|
| 문서 분석 | 문서별 토픽 후보와 키워드 생성 | 임시 토픽 |
| 토픽 통합 | 유사한 임시 토픽을 공통 분류로 병합 | 공통 토픽 ID와 이름 |
| Window 집계 | 시간대와 출처별 문서 수 계산 | 토픽 점유율과 변화율 |
| 요약 | 대표 문서 기반 주요 토픽 설명 생성 | 대시보드용 요약 |

최종 분석에서는 시간대별 뉴스와 댓글의 감정 비율, 토픽별 문서 수, 새롭게 등장하거나 급상승한 토픽과 출처별 반응 차이를 비교합니다.

## 5. Batch 상태 관리

| 상태 | 의미 | 다음 동작 |
|---|---|---|
| `pending` | 분석 대기 | 다음 Batch에 포함 |
| `submitted` | Batch 제출 완료 | 상태 polling |
| `completed` | 결과 다운로드 가능 | 결과 검증·적재 |
| `retry` | 요청 오류·누락·만료 | 재시도 횟수 확인 후 재제출 |
| `failed` | 재시도 한도 초과 | 원인 기록과 수동 검토 |

`custom_id`에는 `event_id`를 연결할 수 있는 안정적인 값을 사용해 입력 문서와 결과를 대응시킵니다.

## 6. Langfuse 관측 계획

Langfuse는 바로 설치하지 않고 관리형과 self-hosted 운영 부담을 먼저 비교합니다. 구체적인 도입 순서는 [멘토 피드백 구현 계획](feedback-implementation-plan.md)의 6·7단계를 따릅니다.

관측 후보:

- 모델과 prompt version
- Batch ID와 문서별 custom ID
- 입력·출력 토큰과 비용
- 제출부터 완료까지의 시간
- 결과 Schema 검증 성공 여부
- 오류·누락·재시도 횟수

Langfuse 기록 실패가 핵심 분석 결과 저장을 중단시키지 않도록 adapter 경계를 두고 오류를 격리합니다. prompt와 응답 원문 저장 여부는 개인정보·원문 정책을 검토한 뒤 결정합니다.

## 7. 안전과 비용 제한

- 작성자 정보와 사용자 식별값을 외부 API로 보내지 않습니다.
- 정제된 분석 대상 텍스트만 요청에 포함합니다.
- 문서별 문자·UTF-8 byte·예상 token 상한을 둡니다.
- 일별 예산 한도 도달 시 신규 Batch 제출만 중단합니다.
- 동일 `event_id`와 prompt version의 중복 분석을 방지합니다.
- 재시도 비용을 최초 요청과 구분해 관측합니다.
